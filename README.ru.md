# llm-lead-qualifier

**Боевой LLM-конвейер, который круглосуточно находит и квалифицирует B2B-лидов. Сначала работают
бесплатные правила, затем двухступенчатый каскад Claude (текст → зрение), затем человек в контуре.
Каждая ступень измеряется против разметки человека.**

[English version](README.md)

Заказчик продаёт премиальную посуду ресторанам. Отделу продаж нужен постоянный поток людей, которые
*решают*, какую посуду покупает кухня: шеф-повара, шеф-кондитеры, а в части регионов — рестораторы и
поставщики HoReCa. Эти люди сидят в Instagram, вперемешку с миллионами фуд-блогеров, домашних кондитеров,
консультантов, аккаунтов заведений и тех, кто сменил работу в прошлом году.

Система читает ~59 000 профилей в день из 15+ источников. 98,4% из них она отсекает бесплатными
правилами, оставшиеся ~0,5% отдаёт Claude, сомнительные — человеку в Telegram, а результат выгружает в
Google Таблицы с разбивкой по отделам продаж.

| Ключевые цифры (15 дней в проде) | |
|---|---|
| Прочитано профилей → сдано лидов | 887 136 → **1 100** (≈73 в день) |
| Доля профилей, дошедших до LLM | **0,62%** (до модели со зрением — 0,21%) |
| Вызовов LLM на сданный лид | **≈0,92** (всего 1 016 вызовов) |
| Точность принятых против разметки заказчика | **83%** (95% ДИ 79–86), n = 595 |
| Полнота дешёвой текстовой ступени | **95%** (92–97): фильтрует, не теряя лидов |
| Валидный по схеме структурированный ответ | 99,2% текст, 99,8% зрение |
| Вердикты сетки «не уверен» → человеку | 9% (177 из 1 902) |
| Разброс цены лида между источниками | **190×** (12 против 2 284 прочитанных профилей на лид) |
| Тесты | 770 (pytest, настоящий Postgres) |

Все метрики и показатели с пояснениями — в [docs/METRICS.ru.md](docs/METRICS.ru.md)

## Как это работает

Схема — в [английском README](README.md#how-it-works). Ниже — по шагам.

1. **Источники дают кандидатов.** Реестры заведений (2ГИС, Афиша, Restoclub) дают рестораны с уровнем
   чека. Веб-поиск строит мост от названия заведения к его Instagram. Шапки заведений называют своих шефов
   («Бренд-шеф @…»). Отметки и подписки расширяют граф. `sources/refill.py` сам переключает источники, когда
   один иссякает.
2. **Воркеры читают профили** через очередь задач в Postgres (`FOR UPDATE SKIP LOCKED`). У каждого
   аккаунта Instagram свой VPN-выход, часовой лимит запросов и охлаждение по эндпоинтам
   (`access/health.py`). Дешёвое чтение уходит анонимным читателям, а аккаунты с сессией остаются для того,
   что без входа не работает.
3. **Бесплатные правила** (`qualify/rules.py`, `qualify/roles.py`, `qualify/vetting.py`) решают
   большинство профилей без модели:
   - есть ли целевая должность в шапке;
   - не аккаунт ли это заведения;
   - не курсы ли, кейтеринг или торты на заказ;
   - работает ли человек сейчас;
   - нужного ли уровня заведение;
   - была ли публикация за последние 6 месяцев;
   - к какому отделу относится город.
4. **Паспорт контакта** (`qualify/passport.py`) отвечает на три вопроса, которые заказчик поднял после
   разбора выгрузки:
   - **Страна.** Зарубежные топонимы, домены, суффиксы ников, украинские буквы и флаг 🇺🇦 взвешиваются
     против российских признаков.
   - **Заведение или человек.** Ловит аккаунты, где «ресторан называет своего шефа».
   - **Дубли.** Находит одного и того же человека под двумя никами.
5. **LLM-каскад** (`llm/grader.py`):
   - **Текстовая ступень.** Claude Haiku читает шапку и 12 подписей у 25 профилей за вызов и отвечает
     `pass | reject | unsure` с причиной в одну фразу. Ступень настроена на полноту и достаточно дешёвая,
     чтобы прогонять всё, что пропустили правила.
   - **Ступень со зрением.** Claude Sonnet смотрит сетку 3×4 из последних 12 постов (`qualify/grid.py`:
     одна картинка вместо двенадцати) рядом с эталонными сетками идеального и пограничного профиля. Отвечает
     `accept | reject | unsure`, даёт уверенность и флаг `strong_profile`.
   - **Маршрутизация.** Отказ окончательный, только если уверенность ≥ 0,75 *и* в сетке ≥ 6 клеток. Всё
     сомнительное уходит человеку.
6. **Человек в контуре** (`ops/bot.py`). Спорные приходят карточками в Telegram с кнопками «берём / нет».
   Последние 20 решений человека подставляются в промпт зрения как few-shot, так что модель подстраивается
   под вкус заказчика без дообучения.
7. **Выгрузка** (`ops/exporter.py`, `ops/sheet.py`) идёт в Google Таблицы по отделам. Каждый отказ
   хранится в отдельной архивной базе с причиной, поэтому любое изменение правил можно прогнать по истории.

## Решения по LLM

| Решение | Зачем |
|---|---|
| **Правила раньше моделей** | 98,4% профилей решаются бесплатно. Бюджет LLM тратится на те 0,6%, где нужно суждение. |
| **Каскад: малая текстовая модель → большая со зрением** | Haiku фильтрует по тексту ~10 профилей за вызов, прежде чем Sonnet потратит вызов с картинкой. Полнота текстовой ступени 95%, так что фильтр почти не теряет лидов. |
| **Сетка 3×4 одной картинкой** | Визуальная планка («подачи, а не инфографика») оценивается по 12 постам за один вход вместо двенадцати картинок. |
| **Структурированный ответ по JSON-схеме** | `--json-schema` с перечислениями вердиктов. Чужие ники в ответе игнорируются, ответ без единого известного ника останавливает цикл, а упавший вызов логируется и никогда не превращается в вердикт. |
| **Порог уверенности и воздержание** | Низкая уверенность, `unsure` или пустая сетка уходят человеку. Модель не принимает окончательных решений, в которых не уверена. |
| **Few-shot из живых решений человека** | Промпт каждый день подстраивается под заказчика без файнтюна. |
| **Промпты ролей в базе** | У каждой роли (шеф, кондитер, консультант, дилер) свои требования в `role_profiles`. Новая роль — это строка в базе, а не деплой. |
| **Замороженные предсказания для eval** | Вердикт оценщика сохраняется до решения человека, поэтому eval меряет модель, а не человека, который её подтверждает. |
| **Дневной лимит вызовов и работа 24/7** | `grader_daily_calls` ограничивает расход. Оценщик работает как сервис и непрерывно разбирает очередь. |

## Evals

Два взаимодополняющих набора.

### 1. Боевой eval на разметке человека (данные закрытые, агрегаты открытые)

`evals/build_gold.py` → `evals/predict.py` → `evals/run.py`

- **Эталон.** Последнее решение заказчика по каждому профилю в боте (595 профилей).
- **Оценка по компонентам.** Для правил, текстовой ступени, ступени со зрением и системы целиком —
  точность, полнота и F1 с **95% интервалами Уилсона**. На сотнях примеров одна точка без интервала вводит
  в заблуждение.
- **Регрессия.** Каждый контакт, на который заказчик указал в реальной выгрузке, становится вечным
  тест-кейсом.
- **Экономика.** Сколько профилей прочитано на один сданный лид, по каналам.
- **Устойчивость.** Проверки Instagram на 1 000 запросов до и после изменения (см. опровергнутую гипотезу в
  [docs/RESULTS.md](docs/RESULTS.md#4-a-hypothesis-the-data-rejected)).

Эталон состоит из профилей реальных людей, поэтому не покидает машину (`evals/data/private/` в
`.gitignore`). Публикуются только агрегаты.

### 2. Синтетический поведенческий eval (открытый, воспроизводимый)

`evals/synthetic.py` генерирует **330 выдуманных профилей в 22 срезах**. Все ники начинаются с `syn_`.
Срезы такие:

- целевые: шеф, кондитер, шапка латиницей, стажировки и родом из-за границы, смешанная лента;
- заграница: Украина, Казахстан, Узбекистан, Грузия;
- аккаунты заведений, в том числе заведение, которое называет своего шефа;
- курсы, кейтеринг, частные и бывшие шефы;
- срезы, которые ловит только суждение: консультанты, фуд-блогеры, travel-шефы.

`evals/offline.py` прогоняет по ним боевые правила и боевой промпт LLM:

```bash
python -m evals.offline          # правила + закэшированные вердикты LLM, без вызовов API
python -m evals.offline --llm    # заново спросить Claude и обновить кэш
```

| Ступень | Точность | Полнота | F1 |
|---|---|---|---|
| Только правила | 67% (58–74) | 86% (78–91) | 75% |
| Только текстовая ступень LLM | 54% (47–61) | 100% (96–100) | 70% |
| **Каскад** | **100% (96–100)** | 86% (78–91) | **92%** |

Ни одна ступень не хороша в одиночку. Правила знают географию и аккаунты заведений, а LLM ловит
блогеров, travel-шефов и консультантов. Отказы объединяются через ИЛИ, поэтому каскад берёт сильные
стороны обеих. Таблица по срезам — в [`evals/results/synthetic_report.md`](evals/results/synthetic_report.md).

#### Итерация промпта, с замером

Первый синтетический прогон показал, что LLM **пропускает 15 из 15 ресторанных консультантов** с ролью
«шеф-повар». Причина — исключение в промпте «консультант без заведения подходит *для роли консалтинга*»:
модель распространила его на все роли. Исключение привязали к своей роли и перепрогнали все 330 случаев:

| | Промпт v1 | Промпт v2 |
|---|---|---|
| `consultant_no_venue` (LLM) | 0% | **100%** |
| Точность каскада | 86% | **100%** |
| Регрессии на целевых срезах | — | нет |

v1 сохранён в `evals/results/synthetic_report_prompt_v1.md` и `evals/data/synthetic_llm_prompt_v1.jsonl`.

#### Найденная, но ещё не исправленная ошибка

`chef_bio_booking_cta`: *личная* шапка шефа вида «Бренд-шеф @venue · бронь в директ» принимается за
аккаунт заведения, называющий своего шефа: слово «бронь» — признак заведения. Правила отклоняют все 15.
LLM отвечает верно, но каскад не может отменить отказ правил. Случай оставлен в наборе как следующая цель:
смягчить правило или отдавать такой шаблон LLM вместо отказа.

## Карта кода

```
leadgen/
  core/      хранилище и обвязка: Postgres (основная + архив), схемы, очередь задач, настройки, тревоги, реплика, бэкапы
  access/    доступ к Instagram: транспорты (с входом / анонимный / HikerAPI), пул аккаунтов, здоровье эндпоинтов,
             часовые лимиты, VPN-выходы по аккаунтам
  sources/   источники: реестры 2ГИС / Афиша / Restoclub, веб-поиск, премии, фестивали, поставщики,
             расширение графа, авторотация источников (refill)
  qualify/   обработчики задач, каталог ролей, бесплатные правила, проверка, паспорт контакта (гео / заграница / дубли),
             разбор имён, сетка из 12 постов
  llm/       оценщик: каскад текст + зрение, схемы, маршрутизация, few-shot, дневной лимит
  ops/       пул воркеров, Telegram-бот (человек в контуре), выгрузка в таблицы, сторож и утренний отчёт
evals/       сборка эталона, предсказатели, метрики (ДИ Уилсона), боевой отчёт, синтетический eval
tests/       770 тестов на настоящем временном Postgres (pgserver или $LEADGEN_TEST_PG)
deploy/      сервисы docker-compose и запуск через launchd на одном Mac
```

Подробно по каждому файлу — в [docs/CODE_MAP.ru.md](docs/CODE_MAP.ru.md). Начинать чтение стоит с `llm/grader.py`, `qualify/vetting.py`, `qualify/passport.py`, `ops/workers.py` и
`sources/websearch.py`.

## Запуск

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m pytest -q          # поднимает временный Postgres через pgserver
python -m evals.offline      # синтетический eval, без сети
```

Для полной системы скопируйте `.env.example` в `.env` и заполните адреса баз, токен Telegram-бота,
сервисный аккаунт Google и `CLAUDE_CODE_OAUTH_TOKEN`. Затем:

```bash
docker compose up -d   # archive-db, workers, registry, grader, bot, backup
```

Секреты живут только в `.env` и `secrets/`. Оба пути исключены из git и docker, а
`tests/test_compose.py` проверяет, что в `.env.example` есть ключи, но нет значений.

## Стек

Python 3.9+, PostgreSQL (psycopg 3; основная база — Supabase), Claude через Claude Code CLI с выводом по
JSON-схеме (Haiku для текста, Sonnet для зрения), httpx с SOCKS, xray для VPN-выходов, Pillow для сеток,
Telegram Bot API, Google Sheets (gspread + Apps Script), Docker Compose / launchd, pytest, GitHub Actions.

## Ответственное использование

Это портфолио-копия системы, сделанной для одного заказчика. Правила Instagram ограничивают
автоматический доступ. Код читает только публичные данные профилей, сам ограничивает темп по каждому
аккаунту и никогда не обходит капчи и антибот-проверки. Логины, куки и файлы сессий в репозиторий не
входят. Фикстуры и синтетический набор выдуманы. Данные реальных людей здесь не публикуются.
